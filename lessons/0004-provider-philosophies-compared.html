Lesson 0004 · AI agent skills for GitHub Copilot

Provider philosophies compared

You have 138 skills installed from four providers. They are not four piles of the same thing: each provider is a different answer to one question — who owns the process while the agent works? This lesson gives you the four answers, the places they collide, and a routing map.

After this lesson you can take any real task and name which provider's flow fits it and why — and you know the four collision domains where two or more providers claim the same job, so you route by name instead of trusting auto-invocation.

1 · One question, four answers

A skill provider is not just a folder of prompts. Each one is a design bet about where engineering judgment should live: in you, in a routing skill, in documents on disk, or in an injected mandate. Put the two extreme answers on an axis first:

flowchart LR
  mp["mattpocock · 39 skills
a toolbox — you pick the tool,
you own the process"]
  pk["pstack · 67 skills
a mandate — the hook injects
poteto-mode, which owns the process"]
  mp ---|"control moves from you to the plugin →"| pk

addyosmani sits between them: the skills are standalone playbooks like mattpocock's tools, but a meta-skill (using-agent-skills) ships a phase map that routes tasks to them — advice, not a mandate:

  mp["mattpocock
toolbox,
you route"]
  ao["addyosmani · 25 skills

that suggests, never injects"]
  pk["pstack
mandate,
the hook routes"]
  mp --- ao --- pk

humanlayer answers the question differently from all three: the process lives in neither you nor a skill but in documents. Its rpi flow writes research, design, and outline artifacts to disk, and each phase runs in a fresh context window that reads them back:

Everything else in this lesson hangs off this axis. The counts are from your disk, not the READMEs: 25 + 67 + 7 + 39 SKILL.md files (pstack ships one more under grok\ — another runtime's slice, same multiplexer pattern as the hooks folder in lesson 3).

2 · Four portraits

addyosmani — the senior engineer's playbook shelf

25 skills, one per engineering discipline: TDD, debugging, security, performance, CI/CD, shipping, API design, observability. Each is a complete standalone playbook with its own quality gates. The README states the bet plainly: skills “encode the workflows, quality gates, and best practices that senior engineers use when building software”, and the meta-skill is blunter still: “Skills are workflows, not suggestions.” (skills\using-agent-skills\SKILL.md). It is the only provider with dedicated security and frontend-engineering playbooks, and it ships four reviewer agents (code-reviewer, security-auditor, test-engineer, web-performance-auditor) plus hooks — though host support for those varies.

pstack — the operating system

67 skills in four layers: 12 workflow drivers (poteto-mode, architect, arena, how, why…), 24 one-rule principle-* leaves, 29 utilities, 2 meta. You know the delivery mechanism from lessons 2–3; the philosophy behind it is in poteto-help: poteto-mode “matches the task to a playbook, copies the playbook's steps into the todo list, and runs the other skills as the steps need them.” Its signature move is spending tokens on rigor — competing design candidates (architect), multi-model bakeoffs with cross-judges (arena), adversarial review panels (interrogate, thermos). The cost is acknowledged, not hidden: “pstack spends extra tokens on subagents and review panels” (skills\poteto-help\SKILL.md).

humanlayer — context engineering as a product

Only 7 skills, but rpi alone bundles five subagents and a document pipeline: research → PRD and/or TDD → structure outline → implementation, each phase writing a numbered artifact to .agents/artifacts/<task>/. The two core rules are stated verbatim in rpi\references\workflow.md: “Documents Carry Context Between Sessions” and “Use a separate context window for each phase by default.” One trap for this course: in rpi, TDD means Technical Design Document, not test-driven development (references\create-tdd\process.md: “Create a Technical Design Document”). Same acronym, unrelated concept — the first provider collision you've met is a vocabulary collision.

mattpocock — the hand-tool drawer

39 skills in four folders (20 engineering, 7 productivity, 8 in-progress, 4 misc): specs, tickets, grilling interviews, TDD, code review, domain modeling — and teach, which built this workspace. The README is an explicit counter-position to the other three: skills are “small, easy to adapt, and composable”, unlike frameworks that “take away your control”, for doing “real engineering - not vibe coding” (mattpocock-skills\README.md). No hooks, no mandate, light cross-references only (tdd points at codebase-design; ask-matt routes on request).

3 · Where they collide

Auto-invocation picks a skill by matching your words against every installed description — the trigger surface from lesson 1. With four providers, several jobs now have two to four claimants:

Domainaddyosmanipstackhumanlayermattpocock
Test-first coding test-driven-development tdd — (its “TDD” is a design doc) tdd
Code review code-review-and-quality thermos, interrogate, thermo-nuclear-* visual-pr (PR prose only) code-review
Planning & breakdown planning-and-task-breakdown, spec-driven-development poteto-mode playbooks, figure-it-out rpi (research → outline) to-spec, to-tickets, wayfinder
Explaining / teaching — teach, how, why show-me teach

The last row is not hypothetical: this very lesson was produced by all three teaching claimants at once — your AGENTS.md routes mattpocock's teach, deepened by pstack's teach and humanlayer's show-me. That is deliberate layering, written down. The first three rows have no such rule yet; today, whichever description happens to match your phrasing wins. Making those collisions deliberate is lesson 6.

The gaps matter as much as the collisions: security and frontend engineering have exactly one dedicated playbook each (both addyosmani), so for those jobs there is nothing to route between.

4 · The routing map

The payoff. Read the left column as “the job in front of me”, not “the provider I like”:

The jobReach forWhy this one
A discipline question mid-task: debug this properly, harden this, optimize this, ship this the matching addyosmani playbook One self-contained playbook per discipline with explicit verification gates; cheap — no subagent fan-out required
A contested design, or an implementation worth real rigor pstack: poteto-mode → architect / arena Competing candidates, cross-model judging, verification culture — deliberately expensive, so reserve it for work that deserves it
A feature spanning days or context windows humanlayer rpi Decisions live in reviewed documents, not chat history; each phase restarts clean and reads them back
Specs, tickets, plan interviews, PR prose, learning mattpocock (to-spec, grilling, pr, teach…) Small composable tools that leave you in charge of the flow
A one-rule course correction mid-task a pstack principle-* leaf 24 single-rule skills, citable from inside any other flow
“Just show me what you mean” humanlayer show-me The smallest diagram or sketch that makes the point — used in every lesson of this course

Notice what the map does not say: it never routes by provider loyalty. mattpocock for prose and pstack for rigor and addyosmani for discipline is the intended end state — curation, not a winner.
