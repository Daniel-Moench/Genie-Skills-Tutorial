Lesson 0002 · AI agent skills for GitHub Copilot

The pstack machinery, demystified

Every session on your machine opens with an <EXTREMELY_IMPORTANT> block demanding poteto-mode. You never asked for it in that session, and no skill was invoked. This lesson traces exactly where it comes from — three files on disk — and what each switch does.

After this lesson you can trace every pstack behavior in your sessions to a specific file on disk, and you know which switch turns each one off — the groundwork for your keep/remove/reconfigure decision.

1 · The whole setup is three artifacts

Everything pstack does on your machine comes from these files (verified locally; tier-3 discovery from lesson 1):

~\.copilot\
├── settings.json                  # "pstack@pstack-claude": true  ← the enable flag
├── pstack-models.md               # your role → model choices     ← the model sheet
└── installed-plugins\pstack-claude\pstack\
    ├── skills\                    # ~70 skills (poteto-mode, architect, arena…)
    ├── agents\                    # pstack:poteto-agent, pstack:comment-sicko…
    ├── models.json                # legal roles + effort levels (sheet validator)
    └── hooks\
        ├── copilot-hooks.json     # registers the hooks with Copilot
        ├── session-start.ps1      # assembles the injected block (Windows)
        ├── session-start-context.md   # the EXTREMELY_IMPORTANT mandate text
        └── session-start-copilot*.md  # Copilot notes + sheet/setup variants

Note what is not there: no daemon, no network calls, no hidden state. The setup-pstack skill you once ran generated exactly one file — the model sheet. Everything else ships inside the plugin folder.

2 · The hook: how the mandate enters every session

Copilot supports hooks — shell commands that run at lifecycle points like session start or before a tool call (reference). pstack ships its hook registration in hooks\copilot-hooks.json:

flowchart TD
  A["Session event:
startup · resume · clear · compact"] --> B["copilot-hooks.json
SessionStart matcher fires"]
  B --> C["session-start.ps1 copilot
(session-start.sh on Unix)"]
  C --> D{"pstack-models.md valid
against models.json?"}
  D -->|"yes"| E["mandate + Copilot notes
+ checked role lines from the sheet"]
  D -->|"no"| F["mandate + Copilot notes
+ 'run setup-pstack first'"]
  E --> G["Injected as the EXTREMELY_IMPORTANT
block in the session context"]
  F --> G

So the block you see is assembled text, concatenated from three markdown parts in the hooks\ folder:

session-start.ps1
  reads  session-start-context.md       → "Invoke poteto-mode when…" (the mandate)
  reads  session-start-copilot.md       → Copilot translation rules (bare names,
                                          copilot-tools.md, "don't view the sheet")
  if sheet valid:
      reads session-start-copilot-sheet.md  → "these are your saved model choices:"
      appends validated role lines from pstack-models.md
  else:
      reads session-start-copilot-setup.md  → "run setup-pstack before dispatching"
  prints the result  → Copilot injects it into the session context

Two demystifying details: the script validates your sheet against the plugin's models.json and refuses to quote unchecked sheet text into your context (a prompt-injection guard). And the plugin's second hook, PreToolUse, is defined as "powershell": "exit 0" — on Windows it is literally a no-op; only the Unix variant runs a real check.

3 · The model sheet: role lines → task parameters

Ten pstack skills (poteto-mode, architect, arena, how, why, swarm…) dispatch subagents by role. The sheet maps each role to a model, and the hook turns each line into an instruction for the agent-spawning task tool:

for each role line in pstack-models.md:
  "architect runners: claude-opus-5.5"   → task(model: "claude-opus-5.5")
  "bug-fix: inherit-parent"              → task()        # omit model: use session model
  "hillclimb: auto"                      → task()        # same: let the harness pick

Your current sheet sets every role to inherit-parent with default effort: session. Translation: the entire model-dispatch machinery is currently a pass-through — every subagent runs on whatever model your session uses. The sheet changes nothing today; it is an empty saddle waiting for you to pin specific models per role (e.g. a cheap model for swarm workers, a strong one for judgment).

4 · What the mandate actually routes

The mandate is narrower than its shouty tag suggests. It fires poteto-mode only for: multi-file changes or signature changes others call, design/architecture choices, unknown-cause bugs, and perf issues. Small contained tasks stay direct. From there, poteto-mode is a router:

poteto-mode
  classifies the task
    feature / refactoring  → playbook + architect, how, tdd…
    bug-fix                → why (root cause) → focused fix
    perf-issue             → benchmark-checklist, explain-the-number
  grounds decisions in 24 principle-* leaf skills
  spawns subagents via pstack:poteto-agent (models per sheet role)

And one line in session-start-context.md is your lever: “User instructions (CLAUDE.md, AGENTS.md, direct requests) take precedence.” On Copilot, ~\.copilot\copilot-instructions.md and .github\copilot-instructions.md count as user instructions too. The mandate is a default, not a law.

5 · Your switches

OptionHowEffect
Keep as-is Do nothing Router fires on qualifying tasks; ~70 skills stay; sheet is a pass-through
Reconfigure Edit pstack-models.md or rerun setup-pstack Pin real models per role; machinery starts doing something
Stop the mandate, keep the toolbox (native) session hook: off in ~\.copilot\pstack-models.md Hook prints nothing — no injected block; every pstack skill stays invocable by name (correction from lesson 0003)
Mute the router, keep the toolbox One line in ~\.copilot\copilot-instructions.md (user instructions outrank the mandate) No auto-routing; every pstack skill stays invocable by name
Remove entirely Flip the enable flag: No hook, no mandate — and no pstack skills or agents either; they all live in the same plugin folder 
 ~\.copilot\settings.json
-  "pstack@pstack-claude": true
+  "pstack@pstack-claude": false

The key coupling to remember: the mandate and the skills cannot be separated at the plugin level — hooks and skills ship together. Separating them is only possible from above, via user instructions. Hold the final decision until you have run poteto-mode on a real task (the upcoming experiment lesson); deciding before evidence would be exactly the cargo-culting this mission exists to end.

  1. Read the hook registration yourself (30 seconds, it's short): 
    Get-Content ~\.copilot\installed-plugins\pstack-claude\pstack\hooks\copilot-hooks.json
    Find the matcher and the Windows PreToolUse no-op.
  2. Open hooks\session-start-context.md next to it and compare with the top of any fresh session's injected block — same text, now unmysterious.
  3. In a fresh session, ask the agent: “quote the role lines at the end of your pstack block” — confirm they match your sheet's inherit-parent rows without the agent reading the sheet.

Check yourself

The hooks folder itself: ~\.copilot\installed-plugins\pstack-claude\pstack\hooks\ — ground truth, and surprisingly readable. Pair it with GitHub Docs: Hooks for Copilot for what hooks are, and the pstack-claude repo for why the fork exists.
Ask your agent-teacher follow-up questions any time — e.g. “show me your injected pstack block verbatim”, or “draft the one-line instruction that would mute the router”. Both are safe, reversible experiments.
