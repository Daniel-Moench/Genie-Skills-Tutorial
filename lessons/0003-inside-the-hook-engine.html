Lesson 0003 · AI agent skills for GitHub Copilot

Inside the hook engine

Lesson 2 called the hooks folder "surprisingly readable" — and you rightly pushed back: it holds 21 files, half of them in awk. This lesson maps the whole folder, explains the awk, and corrects two things lesson 2 oversimplified.

After this lesson you can name which of the 21 hook files actually run on your machine (five), read the Unix tool gate well enough to know what you are not getting on Windows, and you know a fourth off-switch lesson 2 missed.

1 · One folder, ten runtimes

The folder looks complex because it is a multiplexer: one plugin ships hook support for about ten different agent runtimes (Claude Code, Codex, Copilot, Muse, MiniMax, Antigravity, Kimi, OpenCode…). Each runtime reads only its own slice. Yours, on Copilot for Windows, is five files:

~\.copilot\installed-plugins\pstack-claude\pstack\hooks\
│
│  ── runs on YOUR machine ──────────────────────────────────
├── copilot-hooks.json             # the only registration Copilot reads
├── session-start.ps1              # the only code Copilot runs on Windows
├── session-start-context.md       # text part 1: the mandate
├── session-start-copilot.md       # text part 2: Copilot notes
├── session-start-copilot-sheet.md # text part 3a: valid-sheet preamble
├── session-start-copilot-setup.md # text part 3b: "run setup-pstack" fallback
│
│  ── other runtimes' registrations ────────────────────────
├── hooks.json                     # Claude Code
├── codex-hooks.json               # Codex
│
│  ── other runtimes' payload texts ──────────────────────
├── session-start-muse.md / -muse-sheet.md / muse-context.awk
├── session-start-agy.md / agy-context.awk      # Antigravity
├── session-start-minimax.md
├── session-start-opencode.md
├── kimi-instructions.md
│
│  ── the Unix engine (next sections) ─────────────────────
├── session-start.sh               # Unix twin of the .ps1
├── copilot-context.awk            # Unix block assembler
├── json.awk                       # shared JSON parser
├── pre-tool-use.sh                # Unix tool gate entry
├── pre-tool-use.awk               # the gate's verdict logic
└── script-contracts.awk           # allowlist of runnable scripts

So the mental model from lesson 2 survives, sharpened: not "the folder is simple" but "your slice of the folder is simple". The bulk is the same machinery re-targeted at nine other runtimes.

2 · Why awk, of all things

The Unix half is written in awk because the hook must run on any machine with zero installed dependencies — no Python, no Node, no jq. The only scripting languages POSIX guarantees on every Unix are sh and awk. So the author built the tooling from exactly those:

FileRole
json.awk A miniature JSON library: parses the event JSON the runtime pipes into the hook on stdin
copilot-context.awk The Unix block assembler: concatenates the three markdown parts, validates the sheet, rebuilds the role lines — the same job session-start.ps1 does on Windows
pre-tool-use.awk The tool gate's verdict logic (section 4)
script-contracts.awk Declares which plugin scripts the gate may auto-approve, and with which argument shapes
muse-context.awk, agy-context.awk The same assembler, re-targeted at Muse and Antigravity

On Windows there is no POSIX guarantee, so the author wrote one PowerShell twin for the session-start path (session-start.ps1) — and, crucially, did not port the tool gate. More on that in section 4.

3 · The session-start flow, now with all branches

Lesson 2 showed a two-way branch (sheet valid / not). The real flow has three outcomes. First, your very first session ever — no sheet exists yet:

flowchart TD
  A["Session event:
startup · resume · clear · compact"] --> B["session-start.ps1 copilot"]
  B --> C{"pstack-models.md
exists?"}
  C -->|"no"| D["mandate + Copilot notes
+ setup text:
'run setup-pstack first'"]

Once the sheet exists, the script validates every line against the plugin's models.json and splits again:

flowchart TD
  C{"pstack-models.md
exists?"} -->|"no"| D["mandate + notes
+ setup text"]
  C -->|"yes"| E{"every line valid
against models.json?"}
  E -->|"valid"| F["mandate + notes + sheet preamble
+ role lines REBUILT from
parsed values, not quoted"]
  E -->|"invalid"| G["mandate + notes
+ list of problems
+ setup text"]

Two details worth keeping: the role lines in your injected block are reconstructed from validated values — raw sheet text is never quoted into your context (the prompt-injection guard from lesson 2). And the hook fires only on the four matcher events; mid-session nothing re-reads the sheet, which is why sheet edits need a fresh or resumed session to take effect.

4 · The tool gate Windows doesn't have

The second hook, PreToolUse, runs before matched tool calls (view, task, bash). On Unix, pre-tool-use.sh + the two awk files return one of three verdicts:

Tool callVerdictWhy
view of files inside the plugin folder allow Skills constantly read their own SKILL.md files; auto-approving removes dozens of permission prompts
bash running one of 7 allowlisted plugin scripts allow Only if the command matches the exact argument shape declared in script-contracts.awk
task spawning a pstack:* agent with a model not in your sheet deny Hard enforcement: the model sheet is law, not advice
anything else silent No output = fall through to the normal permission flow

And on Windows? The registration says "powershell": "exit 0". That is not laziness — it is the only safe choice. The gate engine is written in sh + awk, which Windows does not guarantee, and in Copilot's hook contract a hook that fails can block the tool call. A port that might error would randomly deny your tools; an unconditional exit 0 is a guaranteed no-op.

The consequences for you are concrete:

  • More permission prompts. Plugin-file views and allowlisted scripts are not auto-approved on Windows.
  • No hard sheet enforcement. On Windows the model sheet is honored only because the injected block asks the agent to — advice, not law. On Unix the gate would deny a violating dispatch.

5 · Correction: there is a fourth switch

Lesson 2's switch table said the only way to stop the mandate without losing the skills was a user-instruction override. Reading session-start.sh disproves that: the script checks your sheet for a session hook: line before assembling anything (session-start.ps1 mirrors it, line 137).

 ~\.copilot\pstack-models.md
-session hook: on
+session hook: off     ← hook prints nothing; no mandate injected

This is a plugin-native off-switch — native to pstack, not to Copilot. Copilot still fires the SessionStart hook every session; the plugin's own script reads the line and exits printing nothing, and empty output means nothing is injected. The plugin stays enabled, all ~70 skills and the agents stay invocable by name, only the injected block disappears. Your updated switch table:

GoalSwitch
Remove everything settings.json → "pstack@pstack-claude": false
Stop the mandate, keep skills (plugin-native) session hook: off in pstack-models.md
Soften the mandate, keep skills (override) Line in ~\.copilot\copilot-instructions.md
Pin models per role Edit the sheet or rerun setup-pstack

Lesson 2 and its reference sheet have been corrected accordingly. The difference between the two middle rows: session hook: off removes the block entirely (the agent never hears about poteto-mode), while a user-instruction override leaves the block in context but outranks it — useful if you want the routing advice visible but not binding.

  1. Map the folder yourself: list the 21 files and sort each into "mine" / "other runtime" / "Unix engine": 
    Get-ChildItem ~\.copilot\installed-plugins\pstack-claude\pstack\hooks -Name
  2. Open pre-tool-use.awk and find the three verdicts — search for the strings allow and deny. Notice what happens in every other case: nothing.
  3. Reversible experiment: set session hook: off in ~\.copilot\pstack-models.md, open a fresh session, and confirm the EXTREMELY_IMPORTANT block is gone. Flip it back to on (your standing decision is to keep the setup as-is until the poteto-mode experiment).

Check yourself
